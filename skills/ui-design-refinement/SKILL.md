# UI 设计优化

把用户要完成的任务转化为可解释的界面调整，并用实际内容检查结果。适用于新页面设计和现有页面改进，采用用户选择的风格与技术栈。

## 从任务与证据开始

先确定目标页面、主要使用者、当前任务和关键操作。读取项目说明、现有组件、样式变量与可用的设计参考，优先复用项目已有规则。用户已给出品牌、风格或布局约束时，将它们作为判断条件。

已有页面能运行时，先查看实际界面；有浏览器工具时记录修改前状态。只有截图时，说明观察限于截图，不推断隐藏交互、权限或接口行为。新页面没有初版时，直接建立内容结构，无需制造错误版本。

把观察与推断分开，例如：“三个动作均为实底色”是可观察现象，“可能增加主操作辨认成本”是待验证影响。不能仅凭侧栏、衬线字体、默认字距或纯色背景存在就判定设计有误。

影响主要操作、安全含义或交付范围的信息缺失时，先获取必要信息；其余可逆选择可依据现有项目推进，并说明关键假设。

## 将判断落实为改动

选择当前最影响任务的一至三个问题，简要说明“观察依据—调整内容—检查方式”。这用于保持修改范围清楚，不要求用户逐步批准常规、可逆的调整。用户只要求评审时，给出意见即可。

优先处理信息与操作，再处理布局、文字和颜色，最后考虑装饰；根据任务灵活取舍。已有结构适用时直接沿用。不要为了用到某个技巧增加无关功能、导航、卡片、渐变或阴影。

实现时使用项目已有组件与有限样式角色。字号、间距、宽度、断点和阴影按实际内容确定，不照搬教学图解的画布数值。

保留准确标签、数据身份、单位和业务状态。原生控件与链接语义、选择关系、键盘焦点等随样式一起维护。权限与执行结果依据现有业务实现，不以按钮外观或静态示例代替服务端判断。

将风格取舍与可用性问题区分。若调整多项属性，用组合结果说明变化；需要判断单项作用时，固定其他条件分别比较。

## 检查后交付

有运行环境时，用修改前后相同数据和接近的视口比较。按改动选择必要检查：长文字、窄屏、文字缩放、加载、空值、失败、焦点或选择状态，避免无关的大范围测试。

颜色判断使用最终前景背景与真实字号。普通文字常见 AA 对比要求为 4.5:1；大号文字为 3:1，大号定义需按实际字号、字重与字体等效条件判断。HSL 明度差、相近色相、浅底深字和灰度图均不能代替对比度计算。细则见参考文档中的 W3C 链接。

能使用浏览器时，查看最终渲染、必要交互和溢出情况；无法运行时，完成可做的代码检查，并明确尚未验证的效果。没有实际测量或用户研究，不写效率提升百分比、无障碍全面达标或“效果必然更好”。

交付简洁说明：改了什么、为什么改、已检查什么、还存在哪些具体限制；提供对应页面、文件或图片。未解决的实质问题继续处理，直到达到用户要求，或准确说明外部阻碍。
